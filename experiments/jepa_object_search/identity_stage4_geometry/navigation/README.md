# HM3D 时钟任务的两次完整导航

两组从同一初态出发，任务要求报告两只不同的时钟。动作预算为 300 步。两组共用 MOST-Nav 的建图和原始任务评分、同一套 Grounding DINO 候选与冻结的 JEPA 身份核验头、APIyi 提供的 `gpt-4o-2024-11-20` 决策服务。对照组只使用原来能读取的关键帧几何。处理组遇到**未选为关键帧**的当前图像时，尝试从旧地图锚点估计相机位姿和候选区域的稀疏深度。两组均保留原来的报告规则和距离要求。

| 时钟任务结果 | 原关键帧接口 | 非关键帧按需估计 |
|---|---:|---:|
| 实际动作 | 300 | 300 |
| 曾进入计分范围的不同目标 | 1 | 1 |
| 报告动作 / 正确报告实例数 | 0 / 0 | 0 / 0 |
| 任务成功 | 否 | 否 |
| 有框并请求身份几何的不同动作步 | 18 | 24 |
| 几何请求（动作步、来源帧去重）| 22 | 33 |
| 其中当前图已被选为关键帧 | 19 | 31 |
| 其中当前图未被选为关键帧 | 3 | 2 |
| 能组成可评分身份输入的请求 | 0 | 0 |
| 成功的上层导航决策 | 31 | 41 |

两次导航的前 115 个动作一致，第 116 个动作出现分歧，早于各自首次身份几何请求。单个开发任务的两条轨迹只能用于定位工程瓶颈。有效性需要在同一次遭遇的相同输入上核验。

表中 22 + 33 共 **55 项**，每项以“运行组、当前动作步、登记来源帧”为单位。同一只钟可在多步触发，多条实例记忆也可能共用同一来源帧。采样器对同一步的同一来源帧保存首次请求的区域，所以这 55 项不能解释为 55 个不同实例、55 次独立身份判定或 55 次可以得分的报告。

### 为什么关键帧也缺几何

两组共有 50 次请求已经选中当前图为关键帧。全部 50 次当时都能读到登记源帧，现场记录的最近可取锚点却落后于当前帧编号。运行结束时，这 50 次请求对应的当前 RGB 均在服务器归档中。原生子图通常等待 17 张关键帧再计算，相邻常规窗口复用一张。时序核查分别还原了两组的全部 17 个子图，并考虑了主动提交短窗口的情况。

| 最早包含当前帧的子图 | 原关键帧接口 | 非关键帧按需估计 |
|---|---:|---:|
| 使用了后续实际动作才产生的帧，提交时建图后端空闲 | 19 | 29 |
| 已收齐图像，提交时后端忙，原地等待可能奏效 | 0 | 2 |

因此，原样等待只能覆盖这 50 个请求中的至多 2 个。另 48 个若要在原地恢复几何，需要改变局部取证方式，例如在核验时用已经观测到的帧提交短窗口。按需估计组只干预未选为关键帧的 2 次请求，两次都有可用的相机高度尺度，都在组装来源图像和地图几何时暂缓。两条运行记录中，身份头均没有获得一组有效输入。

### 第 143 步能否因此得分

对照组在复看路线的第 5 个动作检查登记条目 1，已有两个现场候选框。该条目已通过代理的距离和机位检查；实际运行时因缺少几何，机器人继续向右转。离线使用相同图像、已确定的两个候选框及经地图锚点校验的局部几何，冻结的身份头为条目 1 选择了第 2 个现场框。

当时另外两个登记条目也可能竞争这一现场区域。条目 2 与条目 1 都登记于第 13 帧，但两份原始区域互不重叠，原判定规则将其区分为两个实例。把两份区域分别送入相同的离线几何和冻结身份头，条目 1 再次命中第 2 个现场框，条目 2 暂缓；原版外观模板也没有为条目 2 找到匹配。因此，这名同帧竞争者没有触发区域冲突。条目 3 登记于第 91 帧，而第 143 步的快照只保存了第 13、138、139 帧的几何，完整竞争结果仍未知。

按实际执行链，其他可竞争条目也必须通过排查。已有外观匹配可能产生竞争；不同记忆经身份核验后若认领重叠度至少 0.30 的区域，也会暂缓。通过后，代理才发出 `TARGET_FOUND`。下一步收到该动作的执行回执后才写入已报告记忆，最终由官方评测器按真实位置和此前已获分的目标计算新增实例。第 143 步只验证到局部身份匹配及一名同帧竞争者，实际回合该步没有报告或得分。
